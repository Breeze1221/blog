我用 Astro 建站的第一周，内容全靠手动读文件。

写一个工具函数，扫描目录，读文件，解析头部信息，然后拼成数组。能用，但每次加字段都要改代码，改完还容易漏。

后来换成内容集合，情况变了：字段在配置里声明一次，全站都有类型提示，字段写错了构建时直接报错。

但内容集合也不是银弹。它的约定不少，报错信息有时候很难懂，有些行为和你直觉不一样。这篇把我用下来积累的东西写清楚。

## 一、内容集合解决什么问题

核心问题是：把"内容文件"和"内容结构"分开。

没有集合时，frontmatter 里的字段是自由的。你可以写标题，也可以写 title，可以写日期，也可以写 date。没人管，但读取的时候就得自己兼容各种写法。

有了集合，字段结构在一处声明。声明之后，所有文件都要符合，不符合就报错。读取时拿到的对象有确定的类型。

这带来的最大好处不是校验，而是编辑器里的提示。写 frontmatter 时有补全，读数据时有类型，改字段名的时候能全局找到。

## 二、先看目录结构

约定的目录是源码目录下的内容目录。

下面按集合分文件夹，每个集合一个子目录。一个集合里的文件通常是 Markdown 或者 MDX，也可以是其他格式，取决于配置。

配置文件放在内容目录里，名字是固定的。它负责声明有哪些集合、每个集合的字段结构。

这个结构是约定优于配置的典型。你可以改位置，但改了要同步改配置，不推荐。

## 三、定义集合

在配置文件里，每个集合是一个键值对。

键是集合的名字，值是一个对象，描述这个集合怎么加载、字段长什么样。

加载方式有两种：一种是从目录读文件，一种是从远程数据源拉取。绝大多数场景用前者。

字段定义用的是一个校验库，Astro 内部集成了它。你写的是校验规则，得到的是类型。

## 四、用 schema 约束字段

schema 是集合定义里最重要的部分。

每个字段要声明类型。字符串、数字、日期、布尔、数组、对象，都有对应的写法。

声明之后，校验会在两个时机发生：开发时打开页面，以及构建时。前者给你即时反馈，后者保证上线的内容都是合法的。

我建议把 schema 写得尽量严格。可选字段越少，后面读数据时的判空越少，代码越干净。

## 五、常用的校验写法

标题用字符串，可以加长度约束。

日期用日期类型，它会自动把字符串转换成日期对象，省掉手动解析。

标签用字符串数组，可以加默认值，没写的时候是空数组而不是未定义。

枚举字段用联合类型，限定只能是几个固定值之一。比如分类字段限定为技术、生活、随笔。

可选字段在类型后面加一个可选标记。但我一般尽量不用，而是给默认值。

## 六、默认值和可选的区别

这两个容易混。

可选意味着这个字段可能不存在，读的时候是未定义，代码里要判空。默认值意味着字段一定存在，没写的时候用一个预设值。

从代码整洁的角度，默认值更好。读取时不用判断，类型也不是可空。

什么时候必须用可选？当"不存在"和"有值"是两种不同含义时。比如封面图，没有就是没有，不能用一张默认图代替。

我的原则是：能用默认值就用默认值，只有在语义上确实需要区分时才用可选。

## 七、类型是怎么推导出来的

这是内容集合最舒服的部分。

定义好 schema 之后，读取数据时拿到的对象有完整类型。字段名、字段类型、以及可选性，都能推导出来。

好处是编辑器能提示，写错字段名会报错，访问不存在的字段也会报错。

推导是自动的，不需要手动写类型声明。这让"改 schema"和"改代码"保持一致，不会出现声明和实际不符的情况。

## 八、读取数据的入口

读取用的是一个异步函数，传入集合名。

它返回一个数组，每个元素包含文件内容、解析后的 frontmatter、以及一些元信息比如文件路径和 slug。

因为是异步的，在组件里要用顶层等待。Astro 的组件支持这个写法，不需要额外的状态管理。

返回的数组顺序不保证。这是很多人第一次用会踩的坑：以为按文件名排，实际上不是。

## 九、过滤和排序

拿到数组之后，通常要过滤和排序。

过滤的写法是标准的数组方法。常见的是过滤掉草稿，以及过滤掉未来发布的文章。

排序要小心。日期字段如果是字符串，直接比较字符串是按字典序，不是按时间。一月会比十二月小，因为第一个字符是一。

所以排序前要确保是日期对象。如果 schema 里声明的是日期类型，拿到的就是日期对象，可以直接比较。

## 十、日期字段的陷阱

单独说这个，因为它太常见。

frontmatter 里的日期是一个字符串。如果不声明类型，读出来就是字符串。

字符串比较的坑在于格式不一致。有的写带时区的完整格式，有的写只有年月日。格式不一致，字典序就完全乱了。

声明成日期类型之后，校验库会解析成日期对象。格式不对会直接报错，这是好事，能在构建时发现。

我的习惯是把发布时间写成带时区的完整格式，这样不同地区的人看到的时间一致。

## 十一、slug 从哪来

slug 是文章地址的最后一段。

默认情况下，它来自文件名。文件名是 kebab 形式的英文，slug 就是它。

这个默认值大部分时候够用。但如果文件名是中文，slug 就会变成中文，地址里会出现百分号编码，不好看也不好分享。

所以我的做法是：文件名用英文，标题写中文。两者分开，各司其职。

## 十二、自定义 slug

如果默认规则不满足，可以在 schema 里加一个 slug 字段，手动指定。

也可以在配置里提供一个函数，根据其他字段生成 slug。比如用日期加标题的拼音。

自定义 slug 要注意唯一性。两个文件生成了同一个 slug，构建时可能不报错，但运行时会互相覆盖。

我的做法是在构建脚本里加一步检查，找出重复的 slug 并让构建失败。

## 十三、引用其他集合

内容之间经常有关系。比如一篇文章引用了几个标签，或者引用了另一篇文章。

校验库提供了引用类型，可以指定引用的集合名。写的时候用集合名加标识。

它的价值在于一致性。如果你引用了一个不存在的标识，构建时会报错，而不是在运行时才发现链接是坏的。

这一点在内容多的时候特别重要。手动维护链接，迟早会有死链。

## 十四、引用的代价

引用好用，但不是没有成本。

解析引用需要额外的查找。如果一篇文章引用了很多其他内容，读取时会有多次查询。

在构建时这不是问题，因为构建是一次性的。但如果你的项目用了按需渲染，就要注意这里的开销。

我的建议是：引用用在真正需要一致性的地方。如果只是展示一个标签文字，用字符串就够了，不需要引用。

## 十五、和路由结合

内容集合本身不管路由，路由要靠页面文件。

常见的做法是建一个动态路由文件，用方括号语法表示参数。然后在文件里读取所有内容，生成所有页面。

这个文件要导出两个东西：一个是生成路径的函数，一个是渲染逻辑。

生成路径的函数返回所有可能的路径。构建时会为每个路径生成一个页面。

## 十六、动态路由的写法

生成路径的函数里，读取集合并映射成路径对象。

每个对象包含一个参数对象。参数对象里是路径变量，比如 slug。

渲染逻辑里，用当前路径的参数去集合里找到对应内容，然后渲染。

这里要注意找不到时的处理。理论上不会找不到，因为路径就是从集合生成的。但如果 slug 规则有变化，可能出现不一致。加一个判断更稳妥。

## 十七、渲染 Markdown

集合里的内容可以渲染成 HTML。

渲染函数是异步的，返回一个组件。把这个组件放进页面里就行。

渲染时会应用全局的 Markdown 配置，包括插件、语法高亮、以及各种扩展。这些在站点配置里统一设置。

如果需要针对某个集合用不同的配置，也可以在渲染时传入选项。但这样容易造成不一致，我一般不做。

## 十八、渲染 MDX

MDX 允许在 Markdown 里写组件。

这在内容里需要插入交互元素时很有用。比如嵌入一个图表，或者一个可交互的演示。

代价是构建变慢，因为每个 MDX 文件都要编译。文件多了会明显感觉到。

我的做法是：只有确实需要组件的文章才用 MDX，纯文字的文章还是用 Markdown。

## 十九、自定义渲染组件

渲染时可以指定用哪些组件替换默认的 HTML 标签。

比如把标题替换成带锚点的版本，把图片替换成支持懒加载和响应式的组件，把代码块替换成带复制按钮的版本。

这是内容集合和 UI 结合最紧密的地方。写一次配置，所有文章都受益。

注意替换组件要接受原生的属性，否则会丢失信息。比如图片组件要接受尺寸、替代文本、以及原始的 URL。

## 二十、图片字段怎么处理

图片是内容集合里最容易出问题的一类字段。

如果图片放在公共目录，路径是字符串，直接用就行，但没有优化。

如果图片放在源码资源目录，可以导入，构建时会做优化，产出多尺寸、多格式的版本。但导入是静态的，不能在运行时动态拼路径。

所以图片字段的写法要看需求。要优化就用导入的方式，要灵活就用字符串路径。

我的做法是封面图用导入，因为数量有限且需要优化；文章内的图片用相对路径，交给渲染插件处理。

## 二十一、草稿和发布状态

草稿控制是内容站点的基本需求。

常见做法是在 schema 里加一个草稿字段，布尔类型，默认假。读取时过滤掉草稿。

但要注意：过滤要在所有读取的地方都做。如果某个地方忘了过滤，草稿就会泄露。

更稳的做法是封装一个读取函数，内部统一过滤，所有页面都用这个函数，而不是直接用原始的读取接口。

## 二十二、未来日期的文章

还有一种情况是提前写好、定时发布。

做法和草稿类似：读取时过滤掉发布时间晚于当前时间的文章。

要注意的是这会带来一个副作用：构建时间决定了哪些文章可见。如果站点是静态构建，且构建发生在发布时间之前，那篇文章就不会被生成，直到下次构建。

所以定时发布需要配合定期构建，或者改用按需渲染。

## 二十三、构建时的校验失败

schema 校验失败会让构建失败。这是好事，但报错信息有时候不好懂。

常见报错是"某个字段不符合预期"，但不告诉你具体是哪个文件。需要往上翻日志找文件名。

我的经验是：先在本地跑一次构建，把错误逐个改掉，再提交。不要依赖平台的构建日志，因为反馈太慢。

如果字段很多，可以临时把 schema 放宽，先把构建跑通，再逐步收紧。

## 二十四、数据量大时的性能

内容多了之后，构建时间会上升。

主要成本在两处：解析所有文件的 frontmatter，以及渲染每个页面。

前者的优化空间不大，因为必须读。后者可以优化：延迟渲染、缓存渲染结果、或者只渲染变化的部分。

我的站点内容量不大，没遇到明显瓶颈。但如果要支撑几千篇，就要考虑这些。

## 二十五、从旧方案迁移

如果你原来用的是手动读文件，迁移时要注意几点。

第一是字段名统一。原来可能有 title 和 name 混用，迁移时统一成一个。

第二是补全缺失字段。schema 要求必填的字段，旧文件可能没有，要批量补。

第三是处理格式不一致。日期格式、标签分隔符、以及分类的写法，都可能有多种。

我迁移时写了一个一次性脚本，扫描所有文件，报告不符合 schema 的地方，然后手动逐个修。

## 二十六、和我之前的做法对比

之前是手动读文件加手写类型。

好处是自由，想加什么字段就加什么。坏处是没有约束，字段名拼错、类型写错、必填项漏了，都不会报错，只会在页面上表现为空白。

换成集合之后，这些问题在构建时就暴露了。开发时也舒服很多，编辑器知道每个字段是什么类型。

代价是要多写一份 schema，以及要理解约定。但这份成本是一次性的，收益是长期的。

## 二十七、我踩过的三个坑

第一个是排序。日期没声明成日期类型，排序结果完全不对，查了很久才发现是按字符串比的。

第二个是草稿泄露。有一个页面直接用了原始读取接口，忘了过滤草稿，导致一篇没写完的文章被搜索引擎抓到了。

第三个是 slug 冲突。两篇文章文件名相似，生成的 slug 一样，构建没报错，但访问时总是显示同一篇。

这三个坑的共同点是：不报错，但结果错。这也是内容集合最需要小心的地方。

## 二十八、schema 里的数据转换

校验之外，schema 还能做转换。

常见的用途是规范化：把标签统一转成小写、把多余的空格去掉、把相对路径补成绝对路径。

转换的好处是"进来的数据就是干净的"，后面所有读取的地方都不用再处理。这比在每个页面里各写一遍要可靠。

但转换不要做太重的事。schema 应该只负责格式，不负责业务逻辑。如果在里面读文件、发请求，构建会变慢，而且报错很难定位。

## 二十九、多个集合之间的关系

内容站点往往不止一个集合。

常见的组合是：文章、作者、标签。文章引用作者和标签，作者和标签各自是独立的集合。

这样设计的好处是复用。同一个作者的信息只写一次，改一处就全站生效。标签也能带上描述和图标，而不用在每篇文章里重复。

代价是读取时要多做一次关联查询。构建时可以把作者和标签一次性读出来，做成映射表，避免每篇文章都查一遍。

## 三十、开发时的热更新

改文件之后，开发服务器会自动刷新，这很方便。

但要注意刷新的是什么。改内容文件，页面会更新；改 schema，有时候需要重启服务器才生效。

我遇到过改了 schema 之后校验规则没更新的情况，折腾了半天，最后重启才正常。

如果发现改动没生效，先重启一次开发服务器，再看是不是真的有 bug。这条经验省了我不少时间。

## 三十一、一套可复用的约定

用久了会形成一些固定做法。

我把它们写成了一个模板：固定的字段顺序、统一的日期格式、固定的草稿字段名、以及一套读取工具函数。

新站点直接复制这个模板，省掉每次重新设计的时间。团队成员也按同一套约定写，交接成本低。

约定不需要多，但要稳定。字段名今天叫 cover 明天叫 image，是最耗人的事。

## 三十二、和搜索结合

内容集合的数据，是站内搜索的原料。

常见做法是在构建时把所有文章的标题、摘要、以及正文抽出来，写成一个索引文件，前端加载后用它在本地搜索。

集合在这里的价值是"字段可信"。你知道每篇文章都有标题、都有摘要、都有日期，生成的索引结构就统一，前端不用处理各种缺字段的情况。

如果用了现成的搜索方案，它通常在构建完成后扫描输出目录。这时集合的约束同样起作用：输出结构一致，索引质量就好。

## 三十三、和 RSS 结合

订阅源同理。

生成订阅文件需要文章列表，需要标题、链接、摘要、发布时间。这些都来自集合。

顺序很关键。订阅阅读器按时间排序，如果你的时间字段是字符串，排出来的顺序会乱，读者看到的是"最新一期是三个月前"。

我一开始就犯了这个错，订阅源的顺序完全不对。改成日期类型后立刻正常。

## 三十四、写在最后

内容集合是那种"用对了很省事，用错了很隐蔽"的东西。

它不会阻止你写错，但会把错误提前到构建阶段。这一点对内容站点特别有价值，因为内容站点的错误往往不是崩溃，而是某些页面悄悄地不对。

我现在写新站点，第一步就是把集合和 schema 定下来。字段想清楚了，后面写内容、写页面、写组件都顺。

反过来，如果 schema 草率，后面每加一个功能都要改结构，改结构又要动所有文件。这个成本会一直累积。

所以在开始写第一篇之前，多花半小时想清楚字段，是值得的。

而且这份 schema 是会积累的资产。第一次搭的时候觉得啰嗦，第三个站点的时候就会发现，直接复制过来的那几十行，省掉了所有重新决策的时间。写内容的人只需要关心内容，不用关心结构。
