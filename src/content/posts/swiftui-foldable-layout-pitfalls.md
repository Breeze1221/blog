第一次在折叠设备上跑我写好的界面，出问题的地方并不是我以为的地方。

我以为会坏的是那些写死了宽度的卡片，结果它们只是被拉宽了，难看但可用。真正炸掉的是导航：折叠时是标准的单列推入，展开后应该自动变成左右分栏，可它没有。屏幕明明有 700 多点宽，界面却仍然固执地只用一个 390 点的窄列，右边两百多点全是空白。

那天下午我把这个现象拆开看，才发现自己一直在用一个错的模型理解"自适应"。这篇文章就是这个模型被推翻的过程。

## 一、"自适应"这个词骗了我

SwiftUI 的宣传语里有一个很舒服的词：自适应。听起来像是你把界面交出去，系统会替你安排好一切。

实际情况是：SwiftUI 只负责"测量"和"传递"，不负责"决策"。它会告诉你现在可用空间是多少、尺寸类别是什么、安全区在哪里，但它不会替你决定"这个宽度下应该显示分栏还是单列"。这个决定必须由你写下来。

这一点和 Web 的响应式很像，但有个关键差别。Web 上你写媒体查询，断点是自己定的，失败了很容易看出来——浏览器窗口随便拖一拖就能复现。折叠设备的问题在于，你可能根本没有那台设备，模拟器里切换形态的手感又和真机差很远，于是"没适配"这件事在开发阶段是隐形的。

我后来的做法是把所有和形态相关的判断集中到一个地方，而不是散落在各个视图里。集中之后，至少能一眼看出"这套界面到底为几种形态写了分支"。

## 二、尺寸类别在展开态并不可靠

`horizontalSizeClass` 是我第一个踩的坑。

在手机上它几乎永远是 `.compact`，在 iPad 上根据分屏宽度在 `.compact` 和 `.regular` 之间切换。我理所当然地以为折叠设备展开后就是 `.regular`，于是写了一个很自然的判断：

```swift
if horizontalSizeClass == .regular {
    splitView
} else {
    stackView
}
```

结果展开后仍然是 `.compact`。

原因是尺寸类别是一个"语义"而不是"尺寸"。它表达的是"这个环境适合放多少信息"，由系统根据设备类型、多任务状态、显示缩放等一堆因素综合给出，而不是简单按点数阈值判断。折叠设备展开后的宽高比接近方形，在系统的语义里更接近"大号手机"而不是"平板"，所以它可以合理地继续报 `.compact`。

结论很直接：**不要用尺寸类别做布局分叉的主判据，用实际可用宽度**。尺寸类别可以用来做细节调整（比如内边距、字号档位），但"要不要分栏"这种结构性决定必须看宽度。

## 三、GeometryReader 给的不是你以为的宽度

改用宽度判断之后，我遇到了第二个坑：`GeometryReader` 报出来的宽度比屏幕窄。

原因不复杂，但很容易忽略。`GeometryReader` 报的是"父容器分给我的空间"，不是"屏幕宽度"。如果它被放在一个有内边距的 `VStack` 里，报出来的就已经减掉了内边距；如果上面还有一层 `ScrollView`，情况会更绕。

更麻烦的是，`GeometryReader` 在布局阶段会"贪婪地占满"父容器给的空间。它不会根据子视图的理想尺寸去协商，而是先吃掉全部可用空间再说。所以把一个本来应该按内容自适应的卡片塞进 `GeometryReader`，它就会莫名变成全宽全高。

我最后的做法是尽量避免在结构层用 `GeometryReader`，改用在更外层一次读取，然后往下传。宽度是布局的输入，应该在最上层确定，而不是让每个子视图各自去问。

## 四、折叠缝隙不是一个安全区

折叠设备的中间有一条铰链区，展开态下用户是能看到的。我一开始以为系统会把它算进安全区，于是没做处理，结果一张跨屏的图片正好被折痕劈成两半，人脸分成两半的表情非常诡异。

安全区处理的是"被系统 UI 遮挡的区域"，比如刘海、灵动岛、底部指示条。铰链不是系统 UI，它是一个物理上的不连续面，系统不会自动把它从你的布局里扣掉。

这件事的难点在于，它取决于设备形态和使用姿态。有的设备是"书本式"，折叠时是一条竖线；有的可以悬停成 L 形，此时上半屏和下半屏是两块独立的可用区域。你要处理的不是"一条缝隙"，而是"可用区域可能不连续"。

我的处理原则是：**任何跨越可用区域边界的内容，都必须能容忍被切断**。具体做法是给关键内容留出余量，让它在最坏情况下也不会压在折痕上。这比试图精确计算折痕位置要稳得多，因为折痕位置会随设备、姿态、甚至保护壳变化。

## 五、形态切换会重建视图身份

这是最隐蔽的一个坑，也是我调试时间最长的一个。

界面在展开态下用户填了半天的表单，一折叠，内容全没了。我检查了状态管理，`@State` 明明没被重置，`ObservableObject` 也还在。最后发现是视图身份（identity）变了。

SwiftUI 通过视图在视图树中的位置和类型来判断"这是不是同一个视图"。如果形态切换导致分支从 `if isWide { A } else { B }` 走了另一条，那么 A 和 B 在 SwiftUI 眼里就是两个不同的视图，里面所有 `@State` 都会被销毁重建。

这不算 bug，是 SwiftUI 设计的必然结果。但它和用户的直觉冲突：用户觉得"我只是把手机折起来了，东西应该还在"。

解决办法有两个方向。一是把状态提到视图身份之外，比如放进 `@StateObject` 的模型里，模型由更上层的稳定视图持有。二是让两种形态共用同一套视图结构，只调整布局参数，而不是切换两棵不同的树。

我更倾向第二种。听起来约束更强，但它逼着你把"布局差异"和"内容差异"分开。真正需要不同的往往只是排布方式，不是内容本身。

## 六、NavigationSplitView 的行为比文档复杂

决定用 `NavigationSplitView` 做分栏之后，我以为事情结束了。实际用起来发现它在折叠设备上的行为有一堆边界情况。

第一，列宽是系统管的。你给了 `idealWidth`，但系统会在可用空间不足时自己收缩，甚至把某一列整个折叠掉。这个判断的时机和你的宽度断点不一定一致，于是会出现"我以为该分栏了，它还在单列"或者"我以为该单列了，它已经分栏"。

第二，详情列在无选中项时的占位内容很关键。折叠态下用户看不到它，展开态下它突然出现，如果占位是一个空白页，用户会以为界面坏了。

第三，返回手势和分栏的关系。分栏之后，导航栈的语义变了，用户在详情列里再推入新页面时，是替换详情列还是推出一个新的栈，需要明确设计。

我的经验是：先把"选中态"设计清楚，再谈布局。分栏本质上是把"选中"这个动作可视化，如果没有选中项，分栏就是一具空壳。折叠态下这个问题被隐藏了，展开态下它会暴露得非常彻底。

## 七、键盘和输入法在展开态会咬人

最后一个坑和输入有关。

展开态下屏幕变宽，我按"宽屏"的思路把输入框放在左侧、预览放在右侧。结果键盘弹起来，底部被顶掉一大块，右侧预览被压缩到几乎不可用，左侧输入框的位置也跳了。

问题在于，键盘高度是按屏幕宽度算的，展开态下键盘会占据更大的垂直空间。如果你的布局假设"底部永远有足够空间"，展开态 + 键盘这个组合就会把它击穿。

处理方式不复杂但必须做：让布局对垂直空间也保持弹性，给内容区一个可滚动的最小高度，并且在键盘出现时主动收起次要区域。宽屏不等于"空间充裕"，展开态反而可能是最挤的状态，因为键盘、悬停姿态、多任务都可能同时来抢空间。

## 八、把形态当成三条轴，而不是一个开关

踩完这些坑之后，我重新整理了一遍模型，发现之前所有错误都来自同一个假设：把"折叠/展开"当成一个二元开关。

它其实是三条独立的轴。

第一条是可用宽度。它决定要不要分栏、一屏能放几列、文字行宽是否过长。

第二条是可用区域是否连续。折叠缝隙、悬停姿态都会让可用区域变成两块甚至更多，这决定内容能不能跨越、能不能居中、要不要留余量。

第三条是交互姿态。手持、平放、悬停、外接键盘，对应的是完全不同的输入方式和注意力分布。

三条轴组合起来才是真实场景。只按第一条轴做适配，会得到"看起来对但用起来别扭"的界面；只按第二条轴做适配，会得到"安全但浪费空间"的界面。

## 九、断点应该由内容决定

既然要用宽度判断，那断点定在哪？

很多人的做法是抄一套设备的宽度表，取中间值。我一开始也这么干，后来发现这样定出来的断点没有依据，换个设备就得重调。

更稳的思路是让内容自己说话：找到界面开始"难看"的那个宽度，那就是断点。

具体做法是给每个关键区块测三个值。最小可用宽度，也就是再窄就放不下、必须换布局；舒适宽度，也就是内容排布最自然的位置；最大舒适宽度，超过之后行宽太长、阅读会累。

三个值凑齐，断点自然就出来了。而且这套值不依赖具体设备，未来设备变了，只要内容没变，断点就不用动。

## 十、动画要跟着形态走

形态切换是有动画的，用户能看到屏幕在展开。如果你的布局在同一时刻硬切，视觉上会打架。

我的做法是让布局变化跟随系统的形态过渡，而不是自己起一个动画。形态切换本质上是容器尺寸变化，`withAnimation` 包住状态改变就能让布局插值过去。但要小心，不是所有变化都适合插值。比如从单列切到双列，中间态可能是两列都很窄，看起来像故障。

对于结构性变化，宁可让它在过渡期间保持旧结构，等过渡结束再切换。视觉上会有一个短暂的"滞后"，但比中途出现畸形布局要好。

## 十一、图片和视频的宽高比陷阱

`aspectRatio` 是另一个在宽屏下容易出问题的地方。

折叠态下按 4:3 裁切的封面很好看，展开态下容器变宽，如果仍然按 4:3 拉伸，图片会变成一条横带，主体被裁掉。如果按 `.fill` 铺满，又会把图片放大到模糊。

正确的做法是把"裁切策略"和"容器尺寸"解耦。封面图应该有一个内容感知的焦点，在宽高比变化时优先保住焦点区域，而不是机械居中裁切。这在 SwiftUI 里需要自己算，系统给的 `scaledToFill` 只保证铺满，不保证保住主体。

视频更麻烦，因为播放器的控制条位置、字幕安全区都依赖宽高比。展开态下如果直接从竖屏视频切到横屏容器，用户会看到大量黑边。这时候选择"保持视频原始比例、容器留黑"通常比"拉伸填满"更专业。

## 十二、测试矩阵不能只测两端

我最初只测了两个状态：完全折叠、完全展开。上线后收到的第一个反馈是悬停姿态下界面错位。

悬停姿态是最容易被忽略的状态，因为它既不是折叠也不是展开，而是一个中间形态：上半屏可用、下半屏可用、中间是支撑角。很多界面在这个状态下会同时显示"上半屏的头部"和"下半屏的底部导航"，中间内容被挤没。

测试矩阵至少要覆盖四种：折叠竖持、展开竖持、展开横持、悬停。如果有外接键盘，还要加一种。每种状态下检查三件事：关键操作能不能点到、内容有没有被切断、状态有没有丢。

这听起来很多，但用预览加截图快照能自动化掉大部分。SwiftUI 的 preview 可以指定尺寸，把四种尺寸各出一张快照，提交前肉眼扫一遍，比上线后收反馈便宜太多。

## 十三、手势在形态变化后会失灵

还有一个坑来自手势，而且它非常难查，因为代码看起来完全正确。

我给一个卡片加了拖拽手势，折叠态下拖动手感正常。展开后，卡片变宽，同样的手指位移对应到内容上的比例变小了，用户会觉得"拖不动"。更糟的是，如果卡片跨过了折痕，从一侧拖到另一侧时手指会经过铰链区，系统在那里可能把连续的拖动识别成中断。

手势失灵还有一个隐蔽来源：可点击区域的尺寸。折叠态下按钮占满了窄屏宽度，手指很容易命中；展开后按钮仍然是同样宽度，被放在一个很宽的容器里，视觉上它变小了，但热区如果没跟着调整，用户就会频繁点空。

我的处理方式是把热区和视觉尺寸分开定义。视觉上按钮可以紧凑，但热区要保证一个最小边长，通常是 44 点。这个值在小屏上很容易满足，在宽屏上反而容易被布局压缩掉。

## 十四、性能会因为"多显示一列"而跳崖

展开态多显示一列，听起来只是布局变化，实际上渲染成本是成倍增加的。

折叠态下列表只渲染一屏十几行，展开后同屏可能显示三十行，再加上右侧详情列同时渲染，首帧的构建时间会明显变长。如果列表项里有图片解码、富文本排版、阴影和模糊，这些成本会叠加。

我遇到过一次展开瞬间掉帧，查下来是详情列里的一个高斯模糊背景。它在折叠态下根本没有被创建，一展开就同时做了模糊计算和布局，两个重活撞在一起。

解决办法不是优化模糊本身，而是把重活从"形态切换那一刻"挪走。比如详情列先用一个静态占位背景，等过渡结束再挂上真正的模糊层。用户感知不到差别，但帧率回来了。

这条经验可以推广成一句：**形态切换是性能最脆弱的时刻，任何重计算都不要安排在那一刻**。

## 十五、多任务和折叠会叠加出第四种形态

最后要说的这个坑，我在测试阶段完全没覆盖到。

折叠设备支持分屏多任务。当它和另一个应用并排时，可用宽度会被砍掉一半，此时它既不是"折叠态"也不是"展开态"，而是一个介于两者之间、并且高度也被压缩的新状态。

如果我的断点只按"整屏宽度"设计，这个状态就会落到一个没有专门处理的区间，界面可能出现"分栏了但每列都太窄"的情况。

正确的做法是把可用宽度连续地看待，让布局在任意宽度下都有合理表现，而不是只在几个离散点上正确。这需要断点之间有平滑的降级路径：宽到窄，依次是双列、单列带侧栏、单列。每一级都要能独立成立，不能出现某一级只在特定宽度下才勉强可用。

这也解释了为什么"抄设备宽度表"是危险的。设备表给的是离散的点，而真实环境是连续变化的。

## 十六、一套能落地的检查清单

把所有经验压缩成一份清单，我现在每做一个新界面都会过一遍。

宽度判断用实际可用宽度，不用尺寸类别做主判据。所有结构分叉集中在一处，能一眼数清有几种形态。跨区域内容必须能容忍被切断，不依赖精确的折痕位置。形态切换前后，用户输入的内容不能丢，状态要放在视图身份之外。分栏的前提是选中态设计清楚，没有选中项时要有像样的占位。键盘出现时，垂直空间要按最坏情况留余量。断点由内容的最窄、最舒适、最宽三个值推出来，不抄设备表。结构性变化在过渡期间保持旧结构。图片裁切要有焦点概念，不能机械居中。测试至少覆盖折叠、展开竖、展开横、悬停四种姿态。

清单不长，但每一条背后都是一次返工。

## 十七、把形态写进团队的语言

最后补充一件和代码无关、但影响更大的事：团队里需要有共同的词。

如果每个人都用自己的说法描述形态，"大屏""展开""平板模式"混着用，讨论就会失真。有人说"大屏下按钮要变大"，另一个人理解成"平板尺寸"，第三个人理解成"横屏"，最后做出来的东西哪个都不对。

我现在会在项目文档里固定四个词：折叠态、展开竖、展开横、悬停。每个词对应一组具体的宽度和可用区域描述，讨论时只用这四个词。词定下来之后，很多争论会自动消失，因为大家说的终于是同一件事。

## 十八、最后一点：别把折叠当成加分项

我见过不少团队的适配思路是"先做手机版，折叠屏是加分项，有空再说"。

这个思路的问题在于，折叠设备的用户群体恰恰是最愿意为体验付费的那批人。他们买了更贵的设备，期待的是"更好的体验"，而不是"能打开的界面"。如果展开后只是把手机界面拉宽，他们的失望会比普通用户更强烈。

更重要的是，折叠形态暴露的是设计层面的问题，不是代码层面的问题。一个在折叠屏上表现良好的界面，往往在平板、在桌面、在分屏下也都更稳。因为它被迫想清楚了"我的信息层级是什么""什么可以并排""什么必须独占"。

所以我现在不把它当成适配任务，而当成一次对自己设计的体检。那些在展开态下露馅的地方，通常本来就是设计里含糊的地方，只是小屏幕上被藏起来了。
