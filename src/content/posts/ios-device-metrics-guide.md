做设计交接的时候，最常听到的一句话是"给我一个 375 宽的稿子"。

这句话在五年前基本没问题，现在就不太够了。设备的逻辑宽度有 320、360、375、390、393、402、430、440 这一串，高度更是从 568 一直到 956。你按其中一个做稿，换一台设备就要重新对一遍。

更麻烦的是，很多人在说"分辨率"的时候，指的是三件完全不同的事。有人指逻辑点，有人指渲染像素，有人指屏幕物理像素。三种说法混在一起讨论，最后一定会有人在导出资源时选错倍数。

这篇文章想做的事情很简单：把 iOS 屏幕上这几个概念彻底分开，然后给一套自己推导参数的流程。表会过时，方法不会。

## 一、点、像素、渲染分辨率，是三件事

先从最小的概念开始。

**点（point）** 是布局单位。你在代码里写的 `width: 390`，单位是点。点是一个抽象单位，和物理尺寸没有固定关系，它的作用是让不同密度的屏幕在布局代码里表现一致。

**像素（pixel）** 是显示单位。屏幕由一个个发光单元组成，一个像素就是一个发光单元。物理像素的数量由面板决定，改不了。

**缩放因子（scale）** 是点和像素之间的桥。scale 为 3 时，1 点对应 3 像素。这就是 @3x 的来源。

**渲染分辨率** 是系统实际绘制内容的像素数。它通常等于 逻辑点数 × scale。

**原生分辨率** 是面板的物理像素数。

这里就出现第一个反直觉的地方：渲染分辨率和原生分辨率**不一定相等**。

最著名的例子是早期的 Plus 机型。它的逻辑尺寸是 414×736 点，scale 是 3，所以渲染分辨率是 1242×2208。但那块面板的原生分辨率是 1080×1920。系统先按 1242×2208 渲染，再整体缩小到 1080×1920 输出。

这个"先渲染再缩放"的过程，就是当年 Plus 机型文字看起来略微发虚的原因。它不是 bug，是权衡：让开发者按整数倍切图，同时把面板成本压下来。

理解了这层，你就会明白为什么"我的图是 @3x 的，为什么还是模糊"这种问题会出现。图是对的，但渲染管线里还有一次重采样。

## 二、scale 不是"屏幕清晰度"

很多人把 scale 当成清晰度指标，认为 @3x 一定比 @2x 清晰。这不准确。

scale 只描述"1 点画几个像素"。真正决定观感的，是每英寸有多少像素，也就是 PPI，以及像素和视距的关系。

一台 6.1 英寸、2556×1179 的屏幕，PPI 大约 460。一台 11 英寸 iPad Pro，2388×1668，PPI 大约 264。iPad 的 PPI 低很多，但因为视距更远，观感并不差。

所以在做设计决策时，scale 用来决定切图倍数，PPI 用来判断"这个尺寸在真实视距下够不够细腻"。两者不能互相替代。

我见过一种常见错误：为了"更清晰"，把所有图标都按 @3x 出图，甚至出 4x。结果包体积涨了，屏幕上看起来完全一样，因为渲染管线根本不会用那么多像素。

## 三、逻辑尺寸是连续的，设备是离散的

设备的逻辑尺寸是一张离散表，但你的界面应该按连续空间来设计。

这两句话看起来矛盾，其实是同一件事的两面。设备是离散的，因为硬件就那几款；但用户可能分屏、可能外接显示器、可能用台前调度，可用宽度是连续的。

所以正确的做法不是"为每台设备做一套稿"，而是找到界面的几个关键断点，让界面在断点之间平滑伸缩。

具体怎么找断点，我一般看三个值。

第一个是**内容最小宽度**。再窄下去，卡片里的文字就会挤成两三行，按钮会换行，布局开始难看。

第二个是**舒适宽度**。内容排布最自然的位置，通常是单个文本块 40 到 60 个字符的宽度。

第三个是**最大舒适宽度**。超过它，行太长，眼睛回扫会累，需要引入分栏或增加边距。

三个值一确定，断点自然浮出来，而且和设备表无关。设备更新了，只要内容没变，这套断点还能用。

## 四、安全区不是常量

安全区（safe area）是最容易被硬编码的东西。

有人看到刘海高度是 47 点，就写死 47。换到灵动岛机型，那个区域的实际高度变了；换到没有刘海的 SE，47 点纯属浪费；换到横屏，刘海跑到侧边，垂直方向的安全区又完全不同。

安全区的本质是"被系统 UI 或硬件遮挡、不应放置可交互内容的区域"。它是一个动态计算结果，取决于设备、方向、状态栏显隐、键盘、通话状态等等。

所以正确姿势只有一条：**永远从系统读取，不要自己算**。

在 SwiftUI 里是 `safeAreaInsets`，在 UIKit 里是 `safeAreaInsets` 或 `additionalSafeAreaInsets`。你需要做的是理解它会变，而不是背下它的值。

有一个细节值得注意：安全区会"传染"。父视图如果忽略了安全区去铺满屏幕，子视图拿到的安全区信息可能就不准了。所以放置背景图时可以忽略安全区，但内容层必须重新尊重它，否则内容会被系统 UI 压住。

## 五、刘海、灵动岛和状态栏，是三套不同的东西

这三者经常被当成一个东西讨论，实际上它们的尺寸逻辑完全不同。

**刘海** 是硬件开孔，它决定了顶部安全区的最小高度。这个高度在不同机型上不同，而且横屏时会变成侧边的安全区。

**灵动岛** 是刘海区域的软件化表达，它是一个可以变化的胶囊。静止时很小，展开时可以占据一大片区域。关键是：它有交互，会响应触摸，所以你不能假设"顶部中间这块区域是死的"。

**状态栏** 是系统绘制的时间、信号、电量。它可以被隐藏，隐藏之后安全区会变。它也可以变色，深色背景上要切浅色内容。

把这三者混在一起，会得到"我给顶部留了 47 点，怎么还是被灵动岛挡住"这类问题。正确的心智模型是：顶部安全区 = max(硬件开孔所需, 状态栏高度)，而灵动岛的展开区域是叠在内容之上的临时层，需要额外避让。

## 六、圆角要同心，否则一眼假

圆角半径是最容易露馅的细节。

把一个圆角 16 的卡片放在一个圆角 24 的容器里，如果内边距是 8，视觉上会显得内层圆角"太方"。正确的同心圆角是 外层半径减去内边距：24 - 8 = 16。这个公式在大多数情况下成立。

为什么重要？因为人眼对曲率的连续性非常敏感。两个圆角不同心时，转角处的间距会忽宽忽窄，看起来像贴纸没贴正。这种不适感说不出原因，但用户会觉得"这个界面有点廉价"。

设备本身的屏幕圆角也在变大。全面屏机型的屏幕圆角半径明显大于早期机型，如果你的全屏卡片用了固定的 12 点圆角，在圆角很大的屏幕上，卡片四角会"顶"出屏幕的圆角轮廓，看起来像没对齐。

处理办法是让全屏容器的圆角跟随屏幕，或者在四角留出足够的安全距离，让视觉冲突不那么明显。

## 七、字号不是固定的，Dynamic Type 会放大一切

设计稿上的字号是"默认档"，实际运行时会被 Dynamic Type 缩放。

系统提供七档以上的文字大小，用户可以调到比默认大很多。如果你的布局假设"标题永远是 28 点"，用户调到最大档时，标题可能变成 40 多点，卡片直接撑破。

正确的做法是用语义化字号，比如 `.title`、`.body`、`.caption`，让系统去算实际大小。然后布局要能容忍字号变大：文字允许换行，容器允许撑高，重要的操作不能被挤到屏幕外。

有一个常见的取舍：图标要不要跟着字号放大？我的经验是，图标可以适度跟随，但不要线性跟随。文字放大一倍时，图标放大 1.2 倍通常就够了，否则视觉重心会失衡。

还有一点容易被忽略：行高。字号放大后，行高如果不跟着变，文字会挤在一起，可读性反而下降。语义化字号自带配套行高，这也是它比硬编码字号更可靠的原因之一。

## 八、切图倍数选错，是最常见的资源浪费

@1x、@2x、@3x 三套图，很多人以为"出三套最保险"。实际上现在 @1x 基本没有设备需要了，出它是纯浪费。

判断标准很简单：**看渲染时的 scale**。

scale 为 3 的设备需要 @3x 图。scale 为 2 的设备需要 @2x 图。系统会挑最接近的一套，然后按需缩放。如果只提供了 @3x，在 @2x 设备上系统会缩小它，观感通常可以接受，但会多一次解码和缩放成本。

反过来，只提供 @2x 在 @3x 设备上会被放大，边缘会软。图标这种有锐利边缘的资源，放大后问题特别明显。

我的实践是：**位图出 @2x 和 @3x 两套，矢量图标直接用 PDF 或 SF Symbols**。这样既覆盖了所有设备，又不会浪费。

还有一个坑：切图时把阴影、外发光也画进图里，会导致 @2x 和 @3x 的阴影扩散范围不一致。阴影应该在代码里用图层属性实现，不要烘进图片。

## 九、1px 线在高 scale 下会消失

细线是另一个经典问题。

设计师要求"一条 1 像素的分割线"。你在代码里写 1 点，在 @3x 设备上它就是 3 像素粗，明显比设计稿粗。

正确写法是 `1 / scale`。在 @2x 上是 0.5 点，在 @3x 上是 0.333 点。系统会把它对齐到最近的像素，视觉上接近真正的 1 像素。

但这里还有一个陷阱：对齐。如果线的位置落在半个像素上，抗锯齿会把它渲染成两条半透明的线，看起来像 2 像素的灰线，比实线还显眼。

解决办法是在布局时把线吸附到像素网格。这个操作在不同框架里做法不同，但核心思想一致：先算出目标位置的像素坐标，取整，再换回点。

这类问题在小屏上不明显，在大屏高 PPI 上会被放大，因为像素更细，误差的相对比例更大。

## 十、怎么自己测一台未知设备

设备表会过时，所以更重要的是会测。

第一步，拿到逻辑尺寸。在代码里打印 `UIScreen.main.bounds`，或者用 `GeometryReader` 读最外层容器。注意要读最外层，读内层会得到被内边距削减后的值。

第二步，拿到 scale。`UIScreen.main.scale`，值通常是 2 或 3。

第三步，算渲染分辨率。逻辑宽高乘 scale。这个值可以用来指导切图。

第四步，拿原生分辨率。这个 API 不给，但可以通过截图来看。截图的像素尺寸通常等于原生分辨率，把它和第三步的结果对比，就能判断是否存在重采样。

第五步，测安全区。在四个方向各读一次 `safeAreaInsets`，记下来。你会发现横屏和竖屏的数值完全不同，这就是为什么不能硬编码。

这五步走完，任何一台新设备你都能在十分钟内摸清楚，不依赖任何外部表格。

## 十一、外接显示器和分屏，会引入新的 scale

这是近几年新增的一个维度。

当应用运行在外接显示器上时，scale 可能不是 2 或 3，而是 1 或 2，取决于显示器和缩放设置。如果你的资源只准备了 @2x 和 @3x，在 scale 为 1 的环境里会被缩小使用，图标边缘会糊。

分屏多任务也有类似问题。窗口被压缩后，系统可能改变渲染策略，尤其是当窗口尺寸不是整数倍时。

处理原则是：**不要把 scale 当成编译期常量**。所有依赖 scale 的计算（线宽、对齐、切图选择）都应该在运行时读取。

这条原则在小屏时代可有可无，在多窗口时代是必须的。

## 十二、一张可以自己填的核对表

把上面的内容收成一张表，每做一个界面填一遍。

逻辑宽高是多少，在哪些设备区间内成立。scale 是多少，需要哪几套切图。渲染分辨率和原生分辨率是否一致，有没有重采样风险。四个方向的安全区各是多少，哪些元素需要避让。圆角是否同心，全屏容器是否和屏幕圆角冲突。字号是否语义化，最大档下布局会不会破。细线是否按 scale 换算，有没有落在半像素上。图标是位图还是矢量，放大后是否可接受。有没有考虑分屏和外接显示器的 scale 变化。

表不长，但填完这几项，绝大多数尺寸问题会在开发阶段暴露，而不是在上线后收到"这个界面在某某手机上怪怪的"。

## 十三、半个像素的偏移，比你想的更显眼

尺寸对齐里有一个很细的问题，只在特定条件下暴露，但一旦暴露就很难忽略。

当视图的边角落在一个非整数的像素位置时，系统会用抗锯齿去渲染边缘。对大面积色块来说，这几乎看不出来；但对细线、小图标、文字来说，抗锯齿会让边缘变软，看起来像"没对上焦"。

为什么会落在半个像素上？因为点的坐标可以任意小数，而像素是离散的。点的位置乘以 scale 之后如果不是整数，就产生偏移。

解决方法有两层。第一层是尽量让尺寸和位置用整数点，在 scale 为 2 或 3 的环境下，整数点乘以 scale 一定得到整数像素，天然对齐。第二层是对必须使用小数的场景（比如 1/scale 的细线），主动做像素吸附，把位置取整到最近的像素再换算回点。

这两层做完，你会发现界面"变锐"了。很多人以为是渲染性能提升，其实是消除了不必要的重采样。

还有一类偏移来自父容器的内边距。比如父容器内边距是 13.5 点，子视图从 13.5 开始布局，所有子元素都偏移了半个点。这种误差会累积，越深的层级越明显。定期检查内边距是不是整数，能省掉很多"为什么这块看起来怪怪的"。

## 十四、颜色空间和尺寸一样会骗人

广色域是另一个容易被忽略的维度，它和尺寸没有直接关系，但同样影响"看起来对不对"。

现在大多数 iPhone 的屏幕支持 P3 广色域，而设计稿如果是在 sRGB 空间里画的，同一个十六进制色值在两个空间里的实际颜色并不相同。把 sRGB 的红色直接当 P3 红色用，颜色会显得更艳、更偏。

反过来，如果图片资源被标记成 P3，但在只支持 sRGB 的环境里显示，系统会做色域映射，结果同样不是设计稿里那个颜色。

这带来的实际问题是：同一套颜色，在不同设备上观感不同；设计师改稿时在显示器上看到的效果，和用户在手机上看到的也不同。

处理原则是明确指定颜色空间。品牌色、文字色这类必须稳定的一律用 sRGB；照片、插画这类追求表现力的可以用 P3，但要接受它在老设备上会被压缩。

这件事表面上和"设备尺寸"无关，但它和尺寸共享同一个心智模型：**你以为你写的是绝对值，实际上它是一个在渲染管线里会被转换的相对值**。理解这一点，很多"为什么和我看到的不一样"就能自己解释。

## 十五、横竖屏切换不是简单的宽高互换

最后补一个经常被低估的点：横竖屏切换。

直觉上，横屏就是宽度和高度互换。实际不是。

切换时，安全区会重新计算，刘海可能从顶部跑到侧边。状态栏的行为可能变化，某些机型横屏时会隐藏状态栏。系统 UI 的位置变了，键盘的尺寸也变了。如果界面里有视频播放器，它的控制条布局往往也要跟着换。

更隐蔽的是，切换过程中会有一段时间处于"中间态"，宽度在插值，但布局可能已经按最终值算好了。如果布局在中间态触发了重计算，用户会看到闪烁。

所以横屏适配不能靠"把竖屏的布局参数交换一下"，而要把它当成一个独立的形态去设计。至少要想清楚三件事：安全区在四个方向各自是多少、哪些元素必须重新排布而不是拉伸、切换过程中哪些动画要禁用。

这三件事想清楚，横屏就不会是"竖屏的副产品"，而是一个真正可用的形态。

## 十六、调试覆盖层比截图更可靠

最后说一个实用技巧：做一个尺寸调试覆盖层。

在开发构建里，用一个可切换的浮层显示当前逻辑尺寸、scale、安全区、字号档位。切换设备、旋转屏幕、调字号、开分屏时，这些值实时变化，你能立刻看到界面在什么条件下会出问题。

这个覆盖层的好处是，它把"猜"变成了"看"。你不需要记住哪台设备是什么参数，界面自己会告诉你。

我一般会把它绑在摇一摇或者三指长按上，避免误触，也避免影响正常操作。上线前用编译条件把它整个裁掉，不留任何运行时开销。

## 十七、写在最后

尺寸这件事的难点从来不是记数字。

数字会变，设备会换，表格三个月就过时。真正的难点是建立一套正确的心智模型：点和像素是两层，scale 是桥，安全区是动态的，断点应该由内容决定，切图倍数要跟着渲染走。

还有一个容易被跳过的地方是交接。设计师给开发一份标注稿，如果只写"宽 390"，开发就只能猜这 390 是点还是像素、对应哪个 scale、在别的设备上该缩到多少。标注里至少应该带上三样：逻辑尺寸、导出倍数、该尺寸下的安全区。

这三样东西一旦写清楚，来回确认的次数会肉眼可见地减少。很多所谓的"还原度不够"，根子不在实现，在于一开始双方说的就不是同一个单位。

模型对了，遇到一台没见过的设备，你也能在十分钟内推算出它该怎么适配。模型错了，就算背下整张表，换一台设备还是会翻车。

我现在做新项目，第一件事不是查设备表，而是把调试覆盖层搭起来。让设备自己说话，比背资料可靠得多。参数会骗人，覆盖层不会。把测量这件事交给运行时，把自己解放出来想布局，才是这套方法真正省时间的地方。
