第一次给自己的小工具接大模型 API 时，我按照官方价目表心算了一下：每次请求大概两千 token，一天两百次，一个月应该花不了几十块。

月底账单出来，是这个数的三倍多。

我以为是单价记错了，翻了一遍文档，单价没错。又以为是汇率问题，也不是。真正的原因是：我算的是"我以为发了多少 token"，而账单算的是"服务端实际处理了多少 token"。这两者之间的差距，来自很多我一开始根本没注意的环节。

这篇就写我是怎么把这笔账一点点拆清楚的。方法不复杂，但需要一些工程上的耐心。

## 一、预估和账单对不上的第一层原因

最表层的差异来自计数口径。

我预估时用的是"字符数除以一个系数"，中文按一个字一个 token 粗估。但真实的分词器不是按字切的。中文里常见的词往往是一个 token，生僻字可能拆成两三个，标点、空格、换行各有各的规则。

所以同一个句子，用不同模型的分词器切出来，token 数可能差百分之二三十。我拿中文技术文档测过，粗估的误差普遍在正负两成之间，极端情况下更多。

第二层是系统提示。我预估时只算了用户消息，忘了每次请求都会带上几百 token 的系统提示。一天两百次，光系统提示就是几万 token，一个月下来是相当可观的一笔。

第三层是历史消息。多轮对话里，每一轮都会把之前的内容重新发一遍。我按"单轮"算，服务端按"累积"算，这个差距随对话轮数迅速放大。

## 二、token 到底怎么数才准

要准确，就不能靠估，得用分词器实际切。

主流模型大多提供了分词工具，可以在本地把一段文本切成 token 并返回数量。我现在的做法是：在写代码之前，先用分词器把几段典型文本切一遍，看看实际数量，建立直觉。

比如一段五百字的中文技术说明，我原本以为是五百 token，实际切出来可能是七百到八百。这个偏差如果不修正，所有预估都是错的。

还有一个容易忽略的点：不同模型的分词器不一样。同一个提示词，在 A 模型上是八百 token，在 B 模型上可能是一千。如果要做多模型路由，必须按目标模型分别计数，不能共用一个估算系数。

更省事的办法是直接用服务端返回的用量字段。大多数 API 在响应里会带上本次请求的输入 token、输出 token、以及缓存命中的 token 数。这是唯一权威的数字，我所有的账都以它为准。

## 三、输入和输出的单价差好几倍

价目表上通常有两列：输入单价、输出单价。输出一般贵三到五倍。

这个差价很多人知道，但在设计上忘掉。一个常见的浪费是让模型输出大量不需要的内容。比如要求它"先解释思路再给答案"，如果这个解释你根本不看，那就是在按最贵的单价买废纸。

我后来的做法是把输出结构化：只要结果的地方，就明确要求"只输出 JSON，不要解释"。这一条改动让某些功能的成本降了将近一半，因为输出从几百 token 压到了几十。

反过来，也有该多花的地方。如果任务需要模型展示推理过程才能保证正确率，那这部分输出是值得的。关键是要清楚自己为什么付这笔钱，而不是默认让它自由发挥。

## 四、缓存命中能省多少

缓存是这两年最有价值的一个成本优化点，但它的规则很硬。

原理是：如果这次请求的开头和上次完全相同，服务端可以复用之前的计算结果，对这部分按更低的单价计费，通常是原价的十分之一到二分之一，各家不同。

条件是前缀必须逐 token 一致。差一个字符，从差异点之后全部重新计算。

所以缓存友好与否，完全取决于你怎么组织提示词。稳定内容放前面，变化内容放后面，这是唯一的正确顺序。

我踩过的坑是在系统提示里塞了当前时间。看起来很贴心，实际导致缓存命中率恒为零，因为每次前缀都不同。删掉这一行之后，同样的调用量，账单降了四成。

另一个坑是文件顺序不固定。如果每次拼接上下文时，文件的排列顺序随目录遍历结果变化，前缀就不稳定。解决办法是排序，按文件名或按固定优先级，让顺序可复现。

## 五、重试和失败也在花钱

这个最容易被忽略。

请求失败不代表不计费。有些失败发生在服务端已经开始生成之后，比如超时、连接中断。这种情况下，已经生成的 token 是算钱的，但你什么都没拿到。

更麻烦的是重试。一次请求失败，客户端自动重试三次，如果每次都在中途失败，账单上是三次的费用，而你的日志里可能只记录了一次成功。

我的处理办法是给每次请求打一个唯一 id，把重试次数、每次的用量、最终状态都记下来。这样月末对账时，能看出有多少钱花在了失败上。

实测下来，不稳定的网络环境下，失败重试的成本可能占到总额的一到两成。这个比例不算小，值得专门优化，比如加指数退避、缩短超时、或者换更稳定的接入点。

## 六、流式输出不会更便宜，但体验更好

很多人以为流式输出能省钱，其实不能。流式只是把生成的内容分块返回，token 总量不变，单价也不变。

它改变的是感知延迟。用户看到文字一个个蹦出来，会觉得快；等十秒一次性返回，会觉得卡。对成本没有影响，对体验影响很大。

但流式有一个副作用：计费更难对账。因为内容分块到达，如果中途断开，你拿到的可能是半截，而服务端已经按全部生成计费了。

所以流式场景下，我更依赖服务端返回的最终用量字段，而不是自己数收到的内容。自己数一定会少，因为你永远不知道断掉之后它还生成了多少。

## 七、批处理接口的折扣值不值得

不少服务方提供批处理接口，把一堆请求打包提交，几小时内返回，价格通常是实时接口的一半。

划不划算，取决于你的场景。如果是离线任务，比如批量给历史文章生成摘要、批量打标签，那完全可以用批处理，省一半钱。

如果是用户等着看的实时功能，就不能用，因为延迟不可接受。

我现在的划分是：凡是"用户不在现场等"的任务，全部走批处理；凡是"用户盯着屏幕"的任务，走实时。这条规则简单，但能把成本结构里的可优化部分榨得比较干净。

批处理还有一个隐性成本：结果要靠任务 id 去查，需要额外的轮询和存储。这部分工程量要提前算进去，不能只看单价便宜。

## 八、写一个最小的成本计算器

说了这么多，落到代码上其实很短。

核心是一个函数，接收三个数：输入 token、输出 token、缓存命中 token，再乘以各自的单价，返回这一笔的费用。

关键在于单价要配置化，不要写死。因为模型会调价，不同档位的价格也不一样。我把它放在一个单独的配置里，按模型名索引，改价时只改一处。

第二个关键是单位。价目表通常按每百万 token 报价，而单次请求只有几百上千 token。中间要除以一百万，这个换算很容易错，错一次就是六个数量级的偏差。

第三个关键是精度。用浮点数累加大量小额费用会有累积误差。我见过有人用单精度浮点累加几十万笔，最后总额偏差到几块钱。如果对账要求严格，用定点数或者把金额乘以一万存成整数。

## 九、把用量埋进日志

光有计算器不够，得有数据。

我的做法是每次调用都写一条结构化日志，字段包括：时间、模型、功能名、输入 token、输出 token、缓存 token、耗时、是否重试、是否成功。

这些字段看起来多，但每一个都有用。功能名用来拆账，重试标记用来看失败成本，耗时用来分析性能，成功标记用来算有效成本。

日志写到本地文件或者数据库都行，关键是要能按维度聚合。我一开始只记了总量，后来想按功能拆，发现拆不了，只能推倒重来。

现在我会在调用点显式传入功能名，比如"文章摘要"、"标题生成"、"代码补全"，这样月底能看清每个功能各自花了多少。

## 十、按功能拆账，才知道钱花在哪

有了功能维度，账就清楚了。

我自己的一个项目，总账单里六成花在一个功能上：每次用户打开详情页，都会触发一次"相关内容推荐"，用的是长上下文，输入几千 token。这个功能用户其实很少点，但每次打开都触发。

发现之后，我把它改成手动触发，只有点了"查看更多"才调用。账单立刻降了一半多，用户体验几乎没变。

如果不拆账，我永远发现不了这件事。只会觉得"整体有点贵"，然后去砍一些其实占比很小的功能，砍了半天没效果。

拆账的粒度建议按"用户可见的功能"来分，不要按技术模块分。因为最终做取舍时，你砍的是功能，不是模块。

## 十一、一次请求的完整成本

很多人在算成本时只算模型调用费，实际上还有别的。

网络传输的费用通常可以忽略，但如果走了第三方网关，可能有额外的加价。存储的费用在小规模下可以忽略，但如果你把每次请求的完整上下文都存下来做审计，几个月后就是几百 GB。

还有人力。如果成本优化本身要投入很多工程时间，那要先算清楚能省多少。为了省每月几十块去改一套架构，不划算。

我现在习惯把成本分成三块看：模型费、基础设施费、人力。前两块能算准，第三块只能估。但至少要意识到它存在，不能把优化当成免费的。

## 十二、预算保护不能只靠自觉

人总会忘。所以预算要有硬约束。

最简单的做法是设日限额和月限额，超过就降级或者拒绝。降级可以是切到更便宜的模型，或者返回缓存结果。

复杂一点的做法是按功能设限额。比如某个实验性功能，给它一个很小的额度，用完就停，避免它悄悄吃掉大部分预算。

我还会设异常告警：如果某一天的用量超过过去七天均值的三倍，就发通知。这个规则抓到过好几次问题，包括一次死循环导致的重复调用。

保护机制的价值不在于它经常触发，而在于它触发时能救你。我宁愿它一年触发两次，也不想某天早上看到一张吓人的账单。

## 十三、模型档位不是越贵越好

同一个任务，用不同档位的模型，成本和效果差异很大。

贵的模型在复杂推理上确实更强，但在简单任务上，它和小模型的结果可能没区别，价格却差十倍。

我的做法是分级：把任务按难度分成三档，简单任务用小模型，中等用中档，只有真正复杂的才用大模型。上线前用一批样本测准确率，确认小模型够用就固定下来。

有一个反直觉的发现：某些任务上，小模型加上好的提示词，效果比大模型加烂提示词还好。这说明提示词的质量比模型档位更值得投入。

当然，分级会带来维护成本：要维护多套提示词，要处理路由逻辑。所以只在调用量足够大、成本足够敏感时才值得做。小规模项目直接用最好的模型，省事。

## 十四、成本异常的三个信号

长期看账单，我总结出三个值得警惕的信号。

第一个是单次平均成本上升。总量可能没变，但每次请求变贵了。这通常意味着上下文变长了，或者输出变啰嗦了。

第二个是失败率上升。失败率一高，重试成本就上去了，而且有效产出下降。这时候要看是不是网络问题，或者是不是某个输入触发了模型的异常行为。

第三个是缓存命中率下降。这个最隐蔽，因为账单只是"稍微贵了一点"，不会报警。但命中率从八成掉到两成，费用可能翻倍。要定期看这个指标。

这三个信号我都在监控面板上放了曲线，每周扫一眼，有异常再深挖。

## 十五、从成本反推产品设计

算清楚成本之后，很多产品决策会变得不一样。

比如"免费额度给多少"，以前是拍脑袋，现在是按"单个活跃用户的月均成本"乘以一个系数来定。

比如"要不要做历史对话"，以前觉得是标配，算完发现长对话的累积成本很高，于是改成只保留最近若干轮，更早的自动摘要。

比如"要不要默认开启某个 AI 功能"，算完发现它占了大部分预算但使用率很低，于是改成默认关闭、手动开启。

成本不是一个纯技术指标，它会反过来塑造产品形态。一个每用户每月成本五毛的功能，和一个成本五十块的功能，能做的设计完全不同。

## 十六、我自己的月度复盘表

最后说说我每个月都做的一件事。

我会拉一张表，列几个数：总费用、总请求数、单次均价、缓存命中率、失败率、各功能占比、以及和上月的对比。

这张表不超过十行，但每次看都能发现问题。有一次发现单次均价涨了三成，追下去是因为一次提示词改动把示例从两个加到了八个，每次多带一千多 token。

复盘的意义不是省钱本身，而是保持对系统的感知。成本是一面镜子，它照出的是你的调用模式是否合理、上下文是否臃肿、功能是否有价值。

## 十七、小团队怎么摊这笔账

如果是一个几个人共用一份 API key 的团队，账会变得更麻烦，因为没有天然的归属。

我见过最常见的做法是所有人共用一个额度，月底一起看总数。这样做的后果是没人对成本负责，谁都不觉得自己用得多，于是谁都不优化。

稍微好一点的做法是给每个人发独立的 key，按 key 统计数据。技术上不难，服务方大多支持创建子 key 并单独计量。这样至少能看出谁在烧钱。

更进一步是按项目而不是按人分。同一个人可能同时在做三个项目，其中一个实验性项目烧掉了大部分额度。按项目分账，才能判断哪个项目值得继续投入。

我们团队现在的做法是：每个项目一个 key，每次调用带上项目标识和功能标识，两层维度都能聚合。每月出一张表，贴在共享文档里。公开本身就是一种约束，没人愿意自己的项目长期排在消耗榜第一。

## 十八、自建和托管的选择

当调用量涨到一定程度，会有人提出自建推理服务，说这样更便宜。

这个判断要非常小心。自建的成本不只是显卡，还包括机房、电力、运维、模型更新、以及大量的调优工作。这些加起来，往往比按 token 付费贵得多，除非你的调用量真的很大而且很稳定。

我算过一次：把我当时的用量折算成自建，需要至少两台高配显卡常年开机，加上运维人力，回本周期以年计。而按量付费，我可以随时停掉，没有任何沉没成本。

真正适合自建的场景通常是：数据不能出内网、延迟要求极高、或者用量大到能把固定成本摊薄。这三条不满足任何一条，自建大概率是亏的。

托管服务的溢价，本质上是买弹性。你要为"随时能扩、随时能停"付钱，这笔钱在很多阶段是划算的。

## 十九、成本意识的边界

最后想提醒一句：成本优化是有边界的，过度优化会反噬。

为了省一点 token 把上下文砍到不够用，导致模型频繁答错、用户反复重试，总成本反而更高。为了省模型费切到便宜档位，结果准确率下降，人工返工的成本远超省下的钱。

所以我给自己定了一条线：优化的目标是"单位有效产出的成本"，而不是"绝对花费"。产出没变而花费下降，才是真优化；花费下降但返工变多，那是把钱从账单挪到了时间里，而时间通常更贵。

这条线也帮我拦住了一些看起来很美但没必要的改造。比如有人提议做一套复杂的提示词压缩算法，能把输入压掉三成。我算了算，三成的输入费省下来是每月几百块，而这套算法的维护成本是每月好几天人力，不值得。

知道什么时候不该优化，和知道怎么优化同样重要。前者需要判断力，后者只需要细心，而前者往往更难得。我宁愿把精力放在那些"省下来就是净赚"的地方，比如删掉没人看的输出、关掉没人用的功能，而不是在已经很便宜的环节上反复折腾。

写到这里我想说，成本测算这件事，难点从来不在公式，而在愿不愿意去看。大部分浪费不是算不出来的，是没人去看。把日志埋好，把账拆开，很多问题自己就浮出来了。真正贵的往往不是 token，而是那份"大概差不多"的糊涂。
