我做的第一个带 API 的小工具，鉴权方案是硬编码一个字符串：所有请求都带同一个 key，服务端比对字符串是否相等。

这个方案撑了大概三个月。三个月后，我发现 key 出现在了一个公开的浏览器插件源码里。

原因很简单：前端需要调接口，而前端代码是公开的，写在前端的 key 等于贴在公告板上。

从那之后我重做了一遍鉴权，也慢慢理解了一件事：API key 不是一个字符串，它有一套完整的生命周期。生成只是第一步，后面还有存储、分发、限流、轮换、吊销、以及发现泄露之后怎么补救。

这篇把这套流程完整写一遍。

## 一、一把 key 走天下的问题

最省事的方案是所有调用方共用一把 key。

它的好处是简单：生成一次，到处粘贴。坏处是几乎无法做任何精细管理。

你不知道是谁在调用，因为所有人用的都是同一把。你无法单独吊销某一个人，因为吊销等于所有人一起停。你无法按调用方限流，因为流量混在一起。

一旦这把 key 泄露，你只有两个选择：全部换掉，或者假装没看见。前者会让所有正常调用方中断，后者等于把门敞开。

只要调用方超过一个，就该按调用方分发不同的 key。这是最基本的分界线。

## 二、生成：随机性从哪来

key 的强度取决于随机源。

用时间戳、递增数字、或者自己写的伪随机函数生成的 key，都可预测。攻击者拿到几个样本，就可能推算出规律。

正确的做法是用密码学安全的随机数生成器。标准库通常都有，名字里带 secure 或者 crypto 的那种。它会从系统熵池取随机数，输出不可预测。

长度也要够。常用的量级是 128 位以上的熵，编码成十六进制是 32 个字符，编码成 base62 大约 22 个字符。低于这个量级，暴力枚举的风险就不能忽略。

我现在的做法是：从安全随机源取 32 字节，用 base62 编码，得到大约 43 个字符的 key。足够长，也不会长到影响粘贴。

## 三、前缀不是装饰

好的 key 通常带一个有意义的固定前缀，比如 `sk_live_` 后面接随机串。

这个前缀有实际用途。

第一，它让 key 在日志、截图、代码里可被识别。如果有人不小心把 key 提交到仓库，代码扫描工具可以根据前缀模式检测出来。

第二，它区分环境。`sk_live_` 是生产，`sk_test_` 是测试，一眼就能看出用的是哪个。

第三，它降低误操作。我见过有人把测试 key 配到生产环境，排查了半天才发现。有前缀的话，这种错误在配置时就能看出来。

前缀不提供安全性，但它提供的可识别性，在实际运维中价值很大。

## 四、数据库里不该存明文

key 存进数据库时，如果存的是明文，那么数据库一旦泄露，所有 key 立刻可用。

这类事故在行业里发生过很多次，很多是备份文件被公开，或者某个有读权限的服务被攻破。数据库本身可能很安全，但备份、日志、导出文件都是泄露面。

正确的做法是只存 key 的哈希值，验证时把请求带来的 key 做同样的哈希，再比对。

这样即使数据库泄露，攻击者拿到的是一堆哈希，无法反推出原始 key。

代价是：key 只在生成时展示一次，之后无法再查看。用户忘了只能重新生成。这个体验上的不便，是安全必须付出的成本。

## 五、哈希算法的选择

普通哈希够不够？要看场景。

如果 key 本身是足够长的随机串，那么用快速的哈希算法（比如 SHA-256）就够了。因为暴力破解一个 128 位熵的随机串，计算上不可行，不需要慢哈希来增加成本。

如果 key 是用户自己设的密码，那必须用慢哈希（比如 bcrypt、argon2），因为用户密码熵低，容易被字典攻击。

API key 属于前一种情况，用 SHA-256 就够，不需要加盐。加盐反而会让验证变麻烦：你需要先找到对应的盐，而找盐需要另一个索引。

我现在的做法是：SHA-256 哈希后存库，同时存一个用于查找的短前缀索引，验证时先用前缀缩小范围，再比对完整哈希。

## 六、作用域要具体

key 应该携带权限信息，而不是"有 key 就全能干"。

作用域的设计要具体到操作级别，比如"读文章"、"写文章"、"删除文章"，而不是笼统的"读写"。

具体的作用域有两个好处。一是泄露后的损失可控：一个只有读权限的 key 泄露，攻击者不能删数据。二是审计清晰：你能看到每个 key 实际在做什么。

作用域还要能组合。有些调用方需要读和写，有些只需要读。设计成可选的集合，签发时勾选，比预设几个固定角色更灵活。

我见过的最差设计是只有 admin 和 user 两个角色，结果所有服务都拿 admin，作用域形同虚设。

## 七、限流是 key 的一部分

限流不应该只按 IP，要按 key。

按 IP 限流的问题是，同一个办公室的所有人共用一个出口 IP，一个人跑批量任务，全公司被封。而攻击者换 IP 很容易。

按 key 限流更准确：每个调用方有自己的额度，互相不影响。

额度要分层设置。给正式调用方一个较高的额度，给新签发的 key 一个较低的初始额度，观察一段时间再放宽。这样即使某个 key 被滥用，损失也有上限。

限流的响应也要设计。返回 429 状态码，带上重试等待时间，让调用方能自动退避。不要直接断开连接，那样调用方不知道发生了什么。

## 八、过期和轮换

key 应该有有效期。

永不过期的 key 很方便，也很危险。它一旦泄露，攻击窗口是无限的。

常见的做法是设一个较长的有效期，比如一年，到期前提醒调用方更换。更严格的做法是短期 key 加自动续期。

轮换的难点在于不能中断服务。如果直接让旧 key 失效，调用方会在切换的瞬间报错。

所以轮换需要一个重叠期：新旧两把 key 同时有效，调用方先切到新 key，确认正常后再吊销旧的。重叠期可以是一周，给调用方留出操作时间。

我现在的做法是：签发时就记录到期时间，提前三十天开始在响应头里提示"key 即将过期"，并给出新 key 的获取方式。

## 九、吊销必须立即生效

吊销的安全意义取决于生效速度。

如果吊销之后还有缓存，攻击者仍能继续用几分钟甚至几小时，那吊销就等于没做。

要做到立即生效，验证路径上就不能有长缓存。每次请求都要查一次 key 的状态，或者用一个短 TTL 的缓存（比如几秒），并在吊销时主动清除。

如果为了性能必须缓存，那就要有主动失效机制：吊销事件发生时，向所有验证节点推送失效通知。

这块的工程复杂度不低，但它是安全的基本要求。一个"吊销要等缓存过期"的系统，在事故响应时基本没用。

## 十、泄露检测

key 泄露是必然会发生的事，问题只是什么时候发现。

检测手段有几类。

第一类是模式扫描：在代码仓库、公开的文本里搜索符合 key 格式的字符串。GitHub 这类平台会做自动扫描并通知服务方。

第二类是异常行为检测：某个 key 突然从多个地理位置调用，或者调用量突增，或者开始访问从未访问过的接口。这些都是可疑信号。

第三类是蜜罐 key：故意放一个看起来有效但实际无权限的 key 在某些位置，一旦有人使用，就说明泄露发生了。

我至少会做第一类和第二类。第三类比较重，适合安全要求高的场景。

## 十一、前端绝不能持有 key

这是最常犯的错误，也是最严重的。

前端代码是公开的。打包、压缩、混淆都不能真正隐藏任何东西，因为浏览器必须能执行它，能执行就能被读出来。

把 key 放在前端，等于把密码写在门牌上。

正确的做法是走后端代理：前端调你自己的后端，后端持有 key 去调第三方。前端只携带用户自己的身份凭证，比如登录后的会话。

代理还有一个好处是可以做缓存、做聚合、做限流。前端不需要知道第三方的接口细节。

如果你的应用没有后端，那就要重新考虑方案，而不是退而求其次把 key 放前端。

## 十二、代理怎么写

代理的核心是三件事：鉴权、转发、过滤。

鉴权是验证前端来的请求是否合法，通常靠用户会话或者短期令牌。

转发是把请求发到目标服务，带上服务端的 key。这一步要注意不要透传前端的任意路径，否则代理会变成开放跳板。

过滤是控制返回内容。第三方的响应可能包含内部信息，比如额度、内部 id、错误堆栈。代理要裁掉这些，只返回前端需要的字段。

代理还要有限流，防止单个用户刷爆你的额度。这一层限流按用户维度做，和 key 维度的限流是两回事。

## 十三、环境变量不是保险箱

很多人以为把 key 放进环境变量就安全了。

环境变量只解决了"不写进代码"这一个问题。它仍然会出现在一些地方：进程的启动命令、某些调试接口、崩溃时的内存转储、以及子进程的环境。

在多用户系统上，同一台机器上的其他进程可能读到你的环境变量。

更安全的做法是用专门的密钥管理服务，运行时按需拉取，用完即弃。但对小项目来说这有点重。

实际可行的折中是：环境变量加最小权限运行、避免在日志里打印完整环境、以及定期检查进程列表里有没有意外的暴露。

## 十四、CI 里的凭据

持续集成环境是最容易泄露 key 的地方之一。

常见问题包括：把 key 写进构建脚本、在构建日志里打印、把 key 传给不可信的第三方步骤、或者把含 key 的构建产物上传。

正确做法是用 CI 平台提供的密钥存储功能，只在需要的步骤注入，且默认不打印。

还要注意 fork 出来的 PR。如果 CI 在 PR 上跑，而 PR 来自外部贡献者，密钥绝不能被注入到那个环境。否则任何人都能通过提交一个 PR 来偷 key。

这一条我在配置时专门确认过，因为默认配置下很多平台会注入。

## 十五、多人协作怎么分发

团队里每个人都要用 key 时，分发方式要设计。

最差的做法是把同一个 key 发给所有人。这样无法追溯责任，一个人泄露全体受牵连。

好一点的做法是每人一把，绑定到具体的人。这样出了问题能定位到人，也能单独吊销。

更好的是每人一把加短期有效，配合自动续期。这样即使某人的 key 泄露，窗口也有限。

分发渠道也要注意。不要用聊天工具发 key，聊天记录会被备份、被同步、被截图。用一次性的密钥传递工具，或者让对方自己登录后台生成。

## 十六、日志里不要记 key

日志系统是泄露重灾区。

很多框架默认会记录完整的请求头，而鉴权信息通常在请求头里。于是 key 就被写进了日志文件，然后被备份、被采集、被展示在监控面板上。

处理办法是在日志中间件里对敏感字段做脱敏。匹配到类似的字段名（authorization、api-key、token），就把值替换成前缀加星号，只保留可识别的部分。

还要注意错误日志。异常堆栈里可能包含请求对象，间接带出 key。这类泄露最隐蔽，因为没人会去看堆栈里的请求详情。

## 十七、多环境隔离

开发、测试、生产要用完全不同的 key，不能共用。

共用的风险是：开发环境的日志级别更详细，key 更容易泄露；测试环境可能对外开放，被扫描到；开发者的本地环境更不可控。

隔离之后，即使开发环境的 key 泄露，生产也不受影响。

环境隔离还要体现在数据上。测试 key 只能访问测试数据，不能碰生产数据。这一条要在服务端强制，不能靠约定。

我现在每个环境一个独立的应用注册，独立的 key 集合，独立的额度，互相之间没有任何交叉。

## 十八、一次泄露事故的复盘

说一个我自己的事故。

一个内部工具需要调用第三方 API，我把 key 放在了一个前端页面的配置文件里，想着"这是内部工具，只有同事能访问"。

那个页面后来被加进了一个公开的演示链接里。key 在几周内被扫到，第三方账单上出现了一笔异常消耗。

发现是因为账单告警。处理是立即吊销、换新 key、把调用改成后端代理。

事后总结出三条：内部工具也会被公开；前端永远不能放 key；账单告警是最后一道防线，必须有。

这件事让我把"key 放在哪"变成了一个必须回答的设计问题，而不是随手决定。

## 十九、签名和裸 key 的区别

有一种比裸传 key 更安全的做法，是请求签名。

原理是：客户端持有密钥但不在请求里发送，而是用密钥对请求内容计算一个签名，服务端用同样的密钥重算签名并比对。请求被篡改，签名就对不上。

这种方式的好处是密钥从不上网，即使请求被截获，攻击者拿不到密钥。而且它能防重放，只要签名里包含时间戳和随机数。

代价是签名算法必须在客户端实现，移动端和网页端都要有对应版本，工程量比裸传 key 大。

我的判断是：内部服务之间用裸 key 加 HTTPS 就够了；对外开放的高价值接口，用签名更稳妥。

## 二十、跨域和预检

前端走代理时，会涉及跨域。

浏览器在发真正的请求之前，会先发一个预检请求，询问服务端是否允许。服务端要正确响应预检，包括允许的方法、允许的头部、以及是否允许携带凭据。

常见错误是把允许来源写成星号，同时又允许携带凭据。这两个配置是互斥的，浏览器会直接拒绝。必须明确列出允许的来源。

另一个错误是预检被鉴权中间件拦住了。预检请求不带凭据，如果中间件要求鉴权，预检就会失败，真正的请求根本发不出去。

所以鉴权中间件要放行预检请求，或者把它放在跨域处理之后。这个顺序问题我调过很久。

## 二十一、移动端怎么存 key

移动端的 key 存放比网页端好一些，因为应用代码不是公开可读的。

但也不是绝对安全。应用可以被反编译，key 可能被提取。所以移动端也不应该持有高权限的 key。

可用的方案有几层。系统提供的安全存储，把 key 存在系统密钥链里，其他应用读不到。这一层能防住大部分本地攻击。

再进一步是设备绑定：key 和设备标识关联，换设备就失效。这能防止 key 被复制到别处使用。

最彻底的做法仍然是走服务端代理，移动端只持有用户身份，真正的 key 在服务端。这是唯一能完全避免客户端持有密钥的方案。

## 二十二、审计日志要留多久

出了安全问题，第一件事是查日志。但如果日志只留七天，事故往往发现不了。

审计日志要记录：谁、什么时候、从哪个地址、用了哪把 key、调了什么接口、结果如何。重点是保留时间要够长，至少覆盖一个完整的业务周期。

日志要防篡改。写进去之后不能改，用追加写加校验，或者写到独立的存储里。

访问权限也要控制。审计日志本身包含敏感信息，不是所有人都该看。但也不能只有一个人能看，否则没法互相监督。

我现在的保留策略是一年。一年足够覆盖大部分问题的发现周期，存储成本也在可接受范围内。

## 二十三、安全策略和体验的平衡

每加一道安全措施，就多一分使用成本。

强制短期过期更安全，但调用方要频繁更换，容易因为忘记而中断。要求签名更安全，但接入方要写更多代码，可能因此放弃接入。

我的原则是分层：对内部服务严格要求，因为改动成本可控；对外部接入方放宽，用额度和监控来兜底。

比如对外提供的 key 给一年的有效期，到期前三个月开始提醒，并支持一键续期。同时给每个 key 设调用额度，异常时自动限额，而不是直接封禁。

安全和体验不是二选一，而是按风险分级。把所有场景都按最高标准要求，结果往往是大家绕开你的系统，去做更不安全的土办法。

## 二十四、给自己定一份检查清单

现在每次接入新的第三方服务，我都会过一遍几个问题。

这把 key 会在哪里被使用，是服务端还是客户端？调用方有几个，需不需要分开？权限能不能收窄到只读？有没有设置额度上限？泄露之后能不能在五分钟内吊销？日志里会不会出现它？

六个问题，答完基本就能定下方案。大部分安全问题不是因为不知道怎么做，而是因为没问自己。把这些提问写进接入流程的模板里，比记在脑子里可靠得多。

API key 的管理看起来是小事，但它是所有对外接口的第一道门。这道门设计得好，后面很多问题都不会发生；设计得差，出事时只能手忙脚乱地全量替换。

我现在更愿意在签发流程上多花半天，也不想在事故里熬一个通宵。前者是可控的投入，后者是不可控的损失，两边的账其实很好算。
