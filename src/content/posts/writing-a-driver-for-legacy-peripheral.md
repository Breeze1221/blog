我有一台用了很多年的多媒体控制器，带旋钮、几个按键、还有一个小屏幕。厂商的配套软件五年前就停止更新了，新系统上装不上。

插上电脑，系统能识别到设备，设备管理器里能看到它，但它什么都不做。旋钮转动没有反应，按键按下没有反应，屏幕一直是白屏。

我一开始以为这是个死局。后来想明白，它只是一个 USB 设备，遵循公开的协议规范。协议没变，只是没有软件帮忙翻译。那就自己写一个。

这篇记录整个过程，从看描述符到跑起来，中间踩的坑都在。

## 一、先确认它到底是什么

动手之前要先看清楚设备。

在 Windows 上可以用系统自带的设备管理器看设备信息，在 Linux 上用 `lsusb`，在 macOS 上用系统信息里的 USB 部分。三个平台都能看到厂商 id 和产品 id，这两个数字是设备的身份证。

有了这两个 id，可以去公开的 USB 设备数据库里查，看看有没有人记录过这个设备。如果没有，那就得从描述符开始自己读。

我的设备在数据库里有一条记录，但信息很少，只写了它是一个 HID 设备，没有更多细节。这算是个好开头，说明它用的是标准 HID 协议，不需要厂商专属驱动。

## 二、描述符是一棵信息树

USB 设备连上来时，会向主机报告自己的结构，这套报告就是描述符。

描述符是分层的。最外层是设备描述符，说明厂商、产品、支持几个配置。往下一层是配置描述符，说明功耗、接口数量。再往下是接口描述符，说明每个接口的类别。最底层是端点描述符，说明数据从哪个通道进出。

HID 设备还多一层：报告描述符。它用一套紧凑的字节编码，描述了每个数据包的格式，每个字节的每一位代表什么。

读描述符不需要装驱动，操作系统本身就能拿到。用一些工具可以把整棵树打印出来，看结构比看文档直观得多。

## 三、报告描述符是门小语言

报告描述符是整个项目里最难读的部分。

它不是给人读的，是给解析器读的。每个条目由前缀字节加数据组成，前缀的高位表示数据类型（主条目、全局条目、局部条目），低位表示具体是哪个。

全局条目设定后续字段的通用属性，比如报告长度、逻辑最小值最大值、单位。局部条目设定当前字段的专属属性，比如用途、用途页。主条目定义输入、输出、特征。

读的时候要有耐心，一个字段一个字段地对。我第一次读了三个小时才把整个结构理清楚，中间反复对照规范和工具的输出。

工具会把它翻译成人类可读的形式，我建议先用工具翻译，再回头对照原始字节，这样能建立直觉。

## 四、抓包：先看它在说什么

描述符告诉你"它能发什么"，抓包告诉你"它实际发什么"。

在 Linux 上可以用内核的 usbmon 抓，在 Windows 上需要装过滤器驱动，在 macOS 上相对麻烦一些。我是在 Linux 上抓的，因为工具链最顺手。

抓包的关键是触发动作。转一下旋钮，抓一段；按一下按键，抓一段；什么都不做，也抓一段做对比。

对比能看出来哪些字节在变。变化的位置就是有效数据的位置，不变的是填充或者状态位。

我的设备抓下来是这样的：每个报告 8 个字节，第一个字节是报告 id，第二个字节是旋钮的相对位移，第三个字节是按键位图，后面几个字节是屏幕状态。这个结论花了半天才对上。

## 五、权限是第一道坎

Linux 上默认只有 root 能直接访问 USB 设备。

用 root 跑程序能工作，但这是坏习惯：整个程序都拿到了最高权限，一旦有漏洞，后果很严重。

正确的做法是加一条设备规则，让特定设备对特定用户组可读写。规则文件里写清楚厂商 id 和产品 id，指定所属组和权限位。

规则写完之后要重新加载，并重新插拔设备才生效。这一步我卡了很久，因为改了规则没反应，后来才发现是没重新插。

Windows 上相对简单，HID 设备通常不需要额外权限，普通用户就能读写。macOS 上需要处理输入监控权限，第一次访问会弹窗要用户授权。

## 六、输入报告怎么解析

拿到原始字节之后，要按描述符把它拆成有意义的字段。

我的做法是先定义一个结构，字段和描述符里的用途一一对应。然后写一个解析函数，把字节数组映射到结构体。

解析时要注意字节序。多字节字段可能是小端也可能是大端，描述符里通常会标注，但有些设备标注不规范，要靠抓包验证。

还要注意位对齐。有些字段不是整字节的，比如三个按键占三个 bit，后面跟着五个 bit 的填充。这种字段要按位操作，不能按字节读。

我第一版就是按字节读的，结果按键状态全错，折腾了一晚上才发现是位对齐问题。

## 七、输出报告和反馈

很多设备不只是输入，还有输出。

我的控制器有一个小屏幕，需要主机发指令才能显示内容。输出报告就是干这个的。

发输出报告时要注意，有些设备要求定长，不足的部分要补零，不能短。有些设备对发送频率有限制，发太快会丢包。

还有一个常见的设计是 LED 指示。键盘的 Caps Lock 灯、设备的电源灯，都是靠输出报告控制的。

调试输出报告比较麻烦，因为你不知道设备收到没有。我的办法是先发一个明显的指令，比如让屏幕全亮，用肉眼确认通路是否打通。

## 八、厂商自定义的部分怎么办

标准 HID 只定义了常见的输入类型，比如按键、坐标、旋钮。

超出标准范围的功能，厂商会用自己的方式实现，通常是把数据塞进"厂商自定义"用途页里，或者干脆用私有协议。

这部分没有任何文档，只能靠抓包猜。

猜的方法是对比：操作 A 抓一段，操作 B 抓一段，看差异。差异的字节就是操作的编码。

我的设备上，屏幕内容的更新用了一个私有格式：第一个字节是命令码，后面是参数。我通过反复试验，把几个常用命令试出来了，但还有一些没搞明白，就放着不用。

## 九、中断传输和轮询

HID 设备的数据通常走中断传输。

"中断"这个词容易误解，它不是设备主动打断主机，而是主机按固定间隔来问设备有没有数据。这个间隔叫轮询间隔，在端点描述符里定义。

间隔越短，延迟越低，但占用总线带宽越多。常见值是 1 到 10 毫秒。

我的设备是 10 毫秒，意味着旋钮的最快响应是每秒一百次。实际使用中感觉不到延迟，因为人手转动本来就没那么快。

写程序时不要用忙等去读，要用阻塞读或者异步回调。忙等会占满一个核心，笔记本上很快就发烫。

## 十、跨平台差异比想象中大

同一套逻辑，三个平台的 API 完全不同。

Linux 上可以把 HID 设备当文件读写，路径在 `/dev/hidraw` 下面，读就是 `read`，写就是 `write`，简单直接。

Windows 上要用 HID 相关的系统接口，先枚举设备，打开句柄，再用读写函数。异步要用重叠 IO。

macOS 上走的是 IOKit 框架，需要注册回调，事件驱动。

跨平台的抽象层要设计好，把"打开设备"、"读一个报告"、"写一个报告"这三个操作封装成统一接口，上层逻辑不用关心平台。

## 十一、热插拔要处理

设备会被拔掉，也会被插回来。

如果不处理，拔掉之后程序会卡在读操作上，或者不断报错。

处理方式是监听设备变化事件。Linux 上可以监听系统的设备事件，Windows 上有设备通知，macOS 上有对应的通知机制。

收到"移除"事件就关闭句柄，收到"加入"事件就重新枚举并打开。

热插拔的边界情况很多：拔了立刻插、插了立刻拔、同时插两个同类设备。这些都要测。

我的程序在第一版里，拔掉再插会打开两个句柄，导致同一个事件被处理两次。后来加了去重才解决。

## 十二、多设备共存

如果系统里有多个同类设备，要能区分。

靠厂商 id 和产品 id 是不够的，因为它们相同。要靠设备路径或者序列号。

序列号不是所有设备都有，有些便宜的外设不带。没有序列号时，只能用物理端口路径来区分，也就是设备插在哪个口上。

这个区分方式不稳定，因为换个口路径就变了。但对个人使用来说够用。

我现在的方法是：如果设备有序列号就用序列号做标识，没有就记录端口路径，并在配置里允许手动指定。

## 十三、为什么选用户态

写驱动有两条路：内核态和用户态。

内核态性能最好，延迟最低，但风险最高。一个空指针就能让整个系统崩溃，调试也只能靠日志和重启。

用户态通过系统的 HID 接口访问，性能略低，但安全得多。程序崩了只影响自己，调试可以直接用调试器。

对这类外设来说，用户态的延迟完全够用。10 毫秒的轮询间隔下，多一层用户态的开销几乎感知不到。

所以我毫不犹豫选了用户态。除非你要做一个需要微秒级响应的设备，否则没有理由碰内核。

## 十四、调试工具有哪些

工具有几类，各有用途。

描述符查看器用来读结构，能打印整棵描述符树，也能翻译报告描述符。

抓包工具用来看实际数据流，能按时间排列，能对比不同操作。

十六进制查看器用来手工分析字节，配合抓包用。

日志是最后的手段。在程序里打点，输出每个报告的原始字节和解析结果，出问题时对照。

我建议一开始就把日志打开，把原始数据都记下来。事后分析时，原始数据比解析后的结构有用得多。

## 十五、延迟和缓冲

延迟由几部分组成：设备轮询间隔、传输时间、程序处理时间、界面刷新时间。

前三项通常很小，界面刷新反而是大头。如果每收到一个报告就重绘界面，高频输入会把界面拖垮。

解决办法是节流：数据照收，界面按固定频率刷新，比如每秒三十次。中间的数据合并，只保留最新状态。

缓冲区也要设计。如果处理速度跟不上输入速度，要有策略：丢弃旧数据，还是排队。对实时控制类设备，丢弃旧数据更合理，因为旧的旋钮位置已经没有意义。

## 十六、稳定性：跑三天不拔

功能跑通只是开始，稳定性才是难点。

我让程序连续跑了三天，中间发现两个问题。

第一个是内存缓慢增长，一天涨了几十兆。原因是每次设备重连都创建了新对象，旧对象没释放。

第二个是偶发的读取超时。设备偶尔不响应，程序卡在那里，直到系统超时才恢复。后来加了超时重试和重新打开的逻辑。

这两个问题在短时间测试里都发现不了。稳定性测试必须跑够长，而且要模拟真实使用：拔插、休眠唤醒、系统负载高。

## 十七、文档和回归测试

自己写的东西，过半年自己也会忘。

所以要写文档。写清楚设备 id、报告格式、每个字段的含义、以及哪些命令是猜出来的、哪些是验证过的。

回归测试可以很简单：准备一段录制的原始数据，让解析函数跑一遍，比对输出是否符合预期。这样改代码时能快速发现破坏。

我把抓到的数据存成几个文件，每个文件对应一种操作。测试时读文件、解析、断言。几十行代码，但价值很高。

## 十八、错误处理比功能重要

外设程序的错误分几类，要区别对待。

第一类是暂时的错误，比如读超时。这类错误重试就行，加一个短延迟再试一次，通常第二次就成功。

第二类是永久错误，比如设备被拔掉、句柄失效。这类错误重试没有意义，要关闭句柄，进入等待重连的状态。

第三类是协议错误，比如收到的报告长度不对、报告 id 不认识。这类错误要记录并丢弃这个报告，但不能因为一个坏包就让整个程序退出。

最忌讳的是一出错就退出。用户不会看着日志，他们只会觉得"又坏了"。程序应该自己能恢复，把错误记录下来，继续工作。

## 十九、电源管理和休眠

系统休眠会挂起 USB 设备，唤醒后设备可能不再响应。

我遇到的情况是：合盖休眠，第二天打开，设备还在，但读写全部失败。必须拔插一次才能恢复。

处理办法是监听系统的电源事件。进入休眠时主动关闭句柄，唤醒后重新枚举并打开。

有些系统会在休眠时给 USB 口断电，这种设备醒来相当于重新插入，热插拔逻辑能处理。

还有一种是选择性挂起，系统为了省电会单独挂起某个设备。这个在笔记本上很常见，调试时要特别注意，因为它会让设备"随机"失灵。

## 二十、配置文件放在哪

程序要记住用户的选择，比如旋钮对应哪个功能、屏幕显示什么。

配置存放位置有讲究。放在程序目录里，重装就丢；放在用户目录里，能跟着用户走，符合系统惯例。

跨平台的话，每个系统有自己的约定路径。要按约定放，不要自己发明一个位置，否则用户备份和迁移时会漏掉。

配置的格式建议用可读的文本，比如 JSON 或 TOML。出错时用户能打开看，你也能让他贴过来排查。二进制格式虽然省空间，但排查起来很痛苦。

还要处理配置损坏的情况。文件被改坏了，程序不应该崩溃。读失败就用默认值，并提示用户。

## 二十一、让人用起来的门槛

自己用的工具，也要考虑怎么交给别人。

如果别人要用，第一道门槛是编译。要求对方装编译器、装依赖、跑构建命令，大部分人会在这里放弃。

第二道门槛是权限配置。要写设备规则、要加用户组、要重新登录，步骤一多就没人愿意做。

所以如果打算给别人用，就要把这些打包：提供预编译的二进制，写一个安装脚本自动配置权限，或者在文档里给出复制粘贴就能跑的步骤。

我的这个工具最终只有自己用，所以没做这些。但我很清楚，从"能跑"到"别人能用"，中间隔着的工程量不比写功能本身小。

## 二十二、没有设备时怎么开发

设备只有一台，插在电脑上，但代码要在没有设备的环境里也能测。

办法是把设备层抽象出来。上层逻辑只依赖一个接口：打开、读报告、写报告、关闭。真实设备实现这个接口，测试时换成假实现。

假实现可以读录制好的数据文件，按时间间隔逐条吐出报告。这样就能在没有硬件的情况下跑完整流程，包括界面刷新、错误处理、重连逻辑。

这个设计还有一个好处：换设备时代码不用大改。将来如果买到一个同类的设备，只要写一个新的适配层，上层逻辑原样复用。

我一开始没做这层抽象，逻辑和设备读写混在一起。后来想加测试，发现根本无从下手，只能回头重构。这是一次很典型的教训。

## 二十三、后续维护的打算

这类项目最大的风险不是写不出来，是写完之后没人维护。

系统会升级，接口会变，依赖会过期。过两年再想跑起来，可能要花半天修编译错误。

所以我现在会做几件事。把依赖版本固定住，不要用浮动版本。把构建步骤写进脚本，一条命令能跑起来。在文档里写清楚当时的环境版本，包括系统和编译器的版本号。

这些都不难，但能在将来省下很多时间。一个能长期跑的小工具，比一个功能强大但半年后就跑不起来的工具更有价值。

## 二十四、这件事值不值得做

最后说点实际的。

为一个停产设备写驱动，投入产出比肯定不划算。花的时间足够买好几个新设备。

但它给我的东西是新的设备给不了的。

第一次真正理解了 USB 协议是怎么工作的，第一次知道一个按键按下到程序响应之间发生了什么，第一次体会到"标准"这两个字的分量：正因为协议是公开的，一个停产五年的设备还能被重新唤醒。

这种理解会迁移到别的地方。后来我看任何外设、任何接口文档，都比以前快。因为我知道描述符长什么样，知道数据是怎么组织的，知道该从哪里开始。

至于那台控制器，它现在正常工作。旋钮转起来，屏幕亮着，显示当前的时间和播放状态。它比任何新设备都旧，但它是唯一一个我知道它每一根线在干什么的设备。每天早上坐下，转一下旋钮把音量调小，这个动作和老设备一起，构成了某种只有自己知道的秩序。

写驱动这件事，最后留下的不是代码，是信心。你知道只要协议公开、只要还能抓到包，就没有真正"报废"的硬件。这种信心让我在面对任何陌生的设备时，都不再先想到"这个用不了"，而是先问"它的描述符在哪"。
